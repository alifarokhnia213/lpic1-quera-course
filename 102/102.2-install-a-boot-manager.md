# Install a Boot Manager

#### Key Knowledge Areas:
- Providing alternative boot locations & backup boot option

## Introduction
**Original GRUB** was developed in 1995 Under Gnu Hurd project.

**When a computer is turned on** the first software to run is the Bootloader which is a piece of code with sole purpose of loading the operating system such as Kernel and pass the control to it. The kernel itself will load the necassary modules and drivers, then initialize the hardware and load the rest of the operating system.

**GRUB** and specially GRUB 2 is the bootloader used for most linux distrobutions. it can handle multiple kernel images and parameters as separate menu entries, run arbitrary programs, load windows bootloader and iteract with users by shell and edit boot options or linux parameters before loading them.

**A good Sysadmin** should know the complete bootprocess to be able to control it and recover system from boot failure after a kernel upgrade for example.

## BIOS
**Will do a POST** or (Power On Self Test) and handover the boot process to the first sector of first disk. But MBR is only 512bytes so we need a smart bootloader to handle larger bootmanagers and multiple systems. some of the used boot managers for linux were lilo which is expired and used to be placed in MBR, GRUB legacy and GRUB 2.

## Where is BootLoader
**Historically the IBM Compatible Systems** were using MBR partitioning scheme, created in 1982. in this scheme the first 512bytes of disk is called MBR and contains a table describing the partition table and also a bootstrap code which was called the Bootloader. when a computer turns on this minimal bootloader code is loaded, executed and passes the control of the boot process to a secondary bootloader usually located in the 32kb space between MBR & first partition which in turn will load to os. for example the boot code for grub on MBR will get executed and passes control to a core image between MBR and the first partition and from this point GRUB is capable of loading the rest of the resources like modules and drivers from disk. 

**MBR has the limitation** of 4 primary partitions with maximum of 3 primary partitions with 1 extended partition subdivided into a number of logical partitions and maximum disk size of 2TBs. To overcome these limits, new scheme called GPT (GUID partition table) which was a part of EFI project has been created. 

## GPT 
**(GUID partition table) or GPT** scheme can be used for both BIOS and UEFI systems. On BIOS systems the second part of GRUB is stored in a special boot part and on UEFI, GRUB is loaded from the files `grubia32.efi` for 32bits systems or `grubx64.efi` for 64bits systems from a partition called ESP (EFI System Partition).

## UEFI
**If system is UEFI** bootprocess will follow UEFI stages. it starts with a security phase which checks if OS is safe and can this hardware use this OS to boot the system, and continues untill end where UEFI looks for ESP partition, which is a `FAT32` format partition with PE executables.

**In Both Cases** a binary starts the bootloader and it might be a complete bootloader on `/boot/efi` or a small loader for the main GRUB on MBR, or even a chanloader for windows bootloader.

## Chainload
**Chainloading** is when a bootloader loads another bootloader. such as GRUB loading windows bootloader.

## GRUB
**(Grand Unified Bootloader)** replaced lilo due its limits and hard to touch configuration. grub's first version is called *GRUB legacy* which was started in 1995. the second version of GRUB which was called GRUB 2 is a complete rewrite of first version, started in 2005.

**What is it?** a menu based system where you can choose which bootloader or chainloader to boot. it is also possible to edit menu on the fly or give direct commands from a shell to it.

**chainloading** means giving the control of boot process to another bootloader.

### GRUB Legacy
**it is version 0.97** of first developed GRUB bootloader. usuall installed in `/boot/grub`. main configuration file is in `/boot/grub/menu.lst` but nowadays some distrobutions link this to `/boot/grub/grub.conf`.

**a sample of menu.lst/grub.conf** consists of two sections; the first section contains global configs and 2nd defines different kernel/initram or chainloader or boot options.

#### **GRUB Legacy** Global configs:
- `#` - Comment
- `color` - foreground/background color for items
- `default` - which boot menu item is the default
- `fallback` - which boot menu item should be used if first one fails
- `hiddenmenu` - hide the menu item
- `splashimage` - show this image as splash screen
- `timeout` - wait this much then start booting the default item
- `password` - ask this password
- `saveddefault` - remember the last booted item

Second part of config:
- `title` - defines section name
- `root` - disk/partition where `/boot` is, in the form of `(hddrive,partition)`, say `(hd0,msdos0)`
- `kernel` - kernel image file name in `/boot`
- `rootnoverify` - defines a non-linux root partition
- `chainloader` - another file will act as stage 1 loader. used for booting mostly windows systems.

#### Configure GRUB legacy
Go to `/boot/grub/menu.lst`. a simple sample:

```bash
title <distro-name>
root (hd0,0)
kernel /vmlinuz root=/dev/hda1
initrd /initrd.img
```

#### Chainload other OSs:
GRUB legacy can even be used to load unsupported OSs like windows:

```bash
title windowsXP
root (hd0,1)    # on legacy, partitions start from 0
makeactive
chainload+1
boot
```
**The Parameters**:
- `makeactive`: will set a flag that this is an active partition. this only works on DOS primary partitions.

- `chainload+1`: tells grub to load the first sector of the boot partition because this is where bootloaders are usually located.

- `boot`: will run the bootloader and load the corresponding OS.

#### **GRUB Legacy** commands:
After creating the configuration, you need to install the grub on a disks MBR. the `grub-install` is the command you can use to install the grub; for example if you've got a non-booting system you can use a live CD or rescue drive to boot and run the utility `fdisk -l` to find the boot partition and then install using two different formats:
```bash
grub-install /dev/fd0
grub-install '(fd0)'
```

to install grub it is a good practice to create a temporary mount point under `/mnt` with `mkdir /mnt/tmp` and `mount /dev/sda1 /mnt/tmp` and then run install utility pointing to boot device (not the partition) and mounted directory:
```bash
grub-install --boot-directory=/mnt/tmp /dev/sda
```

if you don't have a dedicated partition but only a `/boot` directory under root file system:
```bash
grub-install --boot-directory=/boot /dev/sda
```

**!Note** that if you want to install the grub anywhere other than MBR, use a chainloader to point your boot sequence toward it.

**If you** needed to change/reconfigure anything during startup, press `e` on that item and you'll get an interactive editing environment. then press `Enter` when you're done and `b` for boot.

#### Interacting with GRUB Legacy:
If you press `c` on grub menu, you will get an interactive shell where you can do lots of things like loading a kernel image with `kernel`, an initrd image with `initrd` or set the root with `root`, then boot the system with `boot` or go back to the menu with `Esc`.

#### Installing grub legacy from shell
**If you need to install GRUB** from shell:
- 1- set the boot device by `boot (hd0,0)`

- 2- if you don't have an idea where the /boot is: `> find /boot/grub/stage1`

- 3- after setting boot partition use `setup` to install grub on MBR and copy the needed files to the disk (not partition): `grub> setup (hd0,0)`

## GRUB 2
**Aimed to be** clearer, safer, more robust and more powerful. it is now the most used bootmanager among BIOS and UEFI systems because it has a much more flexible Configuration with many more commands and conditional statements similar to a scripting language with more modular design. also there is support for themes and graphical boot menus and the ability to boot **Live CD ISOs** directly from hard drive and better support for non-X86 architectures and universal support for UUIDs making it easier to identify disk and partitions and much more ....

**To see disks and partitions by uuid**:
```bash
ls -lh /dev/disk/by-uuid
```

**On BIOS systems** it is installed in `/boot/grub/` or `/boot/grub2` with config file named `grub.cfg`.

**Under UEFI systems** it goes on `/boot/efi/EFI/<DistroName>/` with config file named `grub.cfg` which probably is linked to the one on `/boot/grub/` due to compatability reasons.

**the last GRUB legacy** release is 0.97 and most systems now use GRUB 2 but it is important to know the differences due to the reason that some systems may still use GRUB legacy. 

#### A simplified grub.cfg looks like this:
```bash
set default="0"

menuentry "fedora" {
    set root=(hd0,1)  # on GRUB 2 partitions start with 1 (linux-style)
    linux /boot/vmlinuz root=... ro quiet
    initrd /boot/initrd.img
}

menuentry "windows" {
    chainloader (hd0,msdos2)+1
}
```

**Some of main GRUB 2 options**:
- `menuentry` - defines a new menu entry item
- `set root` - defines where the `/boot` is located
- `linux/linux16` - defines location of kernel on BIOS systems
- `linuxefi` - defines location of kernel on UEFI systems
- `initrd` - defines where initramfs image is located on BIOS systems
- `initrdefi` - defines where initramfs image is located on UEFI systems

**Other GRUB 2 options we may use**:
- `console=` - set the console
- `debug` - start in debug mode
- `init=` - run an specific program instead of default init program.
- `initrd=` - use this initrd
- `ro` - mount the root file system in read-only mode
- `rw` - mount the root file system in read-write mode
- `root=` - use this root file system
- `selinux` - disable selinux on boot
- `single/s/S/1/Single` - boot in single-user mode (SysV)
- `systemd.unit=` - boot in this systemd target

#### GRUB 2 Commands:
```bash
grub-install /dev/sda   # for installation

grub2-mkconfig > /boot/grub/grub.cfg    # after changing the configuration file execute this to make new config

grub-mkconfig -o /boot/grub/grub.cfg    # this also works for making new config file based on /etc/grub.d/ scripts and /etc/default/grub settings
```
**There is also** a `update-grub` command working as a front end of `grub2-mkconfig` & `grub-mkconfig` commands. this way we don't need to output the result of these commands anywhere and by exexution of one command we can update the main config file based on `/etc/grub.d/` (scripts) and `/etc/default/grub` (main settings file).

**!Note** that in modern systems we use both GRUB legacy and GRUB 2 commands and due to compatability reasons one links to another.

#### Options in main settings that controls the behaviour of GRUB 2
**options in `/etc/default/grub`** for GRUB2:

- `GRUB_DEFAULT=`: the default menu entry to boot. it can be numeric like starting from 0, 1 or the name of menu entry like `debian` or `saved` which is explained below.

- `GRUB_SAVEDEFAULT=`: if it is "true" and `GRUB_DEFAULT` is set to "saved", then the boot option will always be the last menu entry that is selected in boot menu.

- `GRUB_TIMEOUT=`: the timeout in seconds. if set to "0" it boots default without showing menu and if "-1" it'll wait untill user selection.

- `GRUB_CMDLINE_LINUX=`: lists commandline options that will be added to entries for the linux kernel.

- `GRUB_CMDLINE_LINUX_DEFAULT=`: by default two menu entries are generated for each linux kernel, one with the default options and one for recovery. with this you can add extra parameters that will be added only to the default entry.

- `GRUB_ENABLE_CRYPTODISK=`: if set to "y" commands like `grub-mkconfig`, `grub-install` and `update-grub` will look for encrypted disks and add commands needed to access them during boot. this disables default and automatic booting because a passphrase is needed to decrypt disks before they can be accessed.

#### Managing menu entries
**New entries can be manually added** to script files within `/etc/grub.d` directory. files should be executable and are processed in numerical order by `update-grub`, therefore "05_debian_theme" is processed before "10_linux". custom menuentries are usually added to "40_custom" file.

**Basic syntax for a manu entry**:
```bash
menuentry "linux" {
    set root=(hd0,1)  # on GRUB 2 partitions start with 1 (linux-style)
    linux /boot/vmlinuz root=/dev/sda ro    # root and ro are linux parameters here
    initrd /boot/initrd.img
}
```

#### Interacting With GRUB 2
**Is so much like GRUB legacy**; if we `e` on an item it will show us an editor window with contents of menuentry as defined in `/boot/grub/grub.cfg`. if we push `c` on menu we get a shell where we can execute commands like `root`, `linux`, `initrd` and `boot`.

**on GRUB cmd** we can use `help` command to show available commands and use `tab` to autofill when entering a command or parameter. use `ls` to list available disk devices and partitions.

**`ls (hd0,msdos1)/` will show us** contents of a partition's file system.

#### Kernel Boot Parameters
**On examples above we had a line like this:**
```bash
linux /boot/vmlinuz root=/dev/sda ro quiet
```
all things coming after choosing kernel image is a sort of GRUB boot parameters. like `root` tells linux which device to use for root filesystem, `ro` tells to open it as **read-only** and `quiet` tells linux that **Do not show much logs** to the user while booting up the system.

#### Booting from rescue
**In case of failure, GRUB 2** may show us a rescue shell. we can notice it by `grub rescue>`. the process of booting a system from this shell is almost the same as shown before. however we will need load a few GRUB 2 modules to make things work. after finding out which partition is boot partition:
```bash
grub rescue> set prefix=(hd0,msdos1)/boot/grub

grub rescue> insmod normal
grub rescue> insmod linux
```
and next will be as before:
```bash
grub rescue> set root...
grub rescue> linux /vmlinuz ...
grub rescue> initrd /initrd.img
grub rescue> boot
```

## The Boot partition
**On Linux**, files necessary to boot the system are stored on `/boot` mountpoint. in todays systems, GRUB can mount root filesystem and look for files inside `/boot` directory, but a good practice is to separate these files from rest of the disk and filesystem and put them inside the first partition of the disk ensuring that machine can always locate it and boot the kernel.

**Linux distros do not** put actuall kernel & initrd at the root directory of root filesystem. instead these are links to the actual files inside /boot directory or partition.

#### Contents of the boot partition
**Contents** of `/boot` directory may vary based on System Architecture or Boot Loader in use. most of them are named with the version of corresponding kernel. for example a config file for kernel version `4.15.0-65generic` would be called `config.4.15.0-65generic`

- **Config file**: stores config parameters for kernel. it is generated automatically when a new kernel is compiled and installed so it is not safe for us to change it or modify it.

- **System Map**: this file is a look-up table matching symbol names (like variables/functions) to their corresponding position in memory. this is useful when debugging a kind of system failure known as kernel panic as it allows user to know which variable or function was being called when the failure occured.

- **Linux Kernel**: `vmlinuz-4.15.0-65-generic` is the OS kernel. you may also find `vmlinux` as when the file has not been compressed.

- **Initial Ram Disk**: Contains a minimal and temporary root file system loaded into RAM disk containing utilities and kernel modules needed so kernel can mount the main root file system.

- **Bootloader files**: on a system with GRUB installed these are usually located on `/boot/grub` and includes configuration files for the boot loader.
